## 训练 & 精度

### Q1 · 为什么我用 v8s 微调，AP 反而比原版权重低？

99% 是这三个原因：

1. **学习率太大**：预训练权重是 `lr0=0.01` 训出来的，微调时用同样的 0.01 会把预训练分布"洗掉"。改成 `lr0=0.001` 甚至 `0.0005`，`warmup_epochs=3`。
2. **训练轮次太少**：YOLO 的收敛曲线长尾很长，5 个 epoch 只到 60% 最优。**至少 50 epoch，理想 100 epoch**。
3. **数据集和 COCO 差距大**：COCO 是自然场景，你微调的是俯拍工业图，视觉分布差异大。这时应该 `epochs=100+`、`imgsz` 从 640 涨到 1024 或 1280，让模型重新学习尺度分布。

**参考**：[训练调优指南](/recipes/train)

### Q2 · 为什么 v11 比 v8 训练慢，但推理快？

**训练慢**：v11 的 `C3k2` 骨干比 v8 的 `C2f` 参数少但**计算路径更长**（更深、更粗粒度），FLOPs 反升了约 30%。训练时 GPU 利用率反而降。

**推理快**：v11 支持**结构重参数化**（训练时用多分支，推理时融合为单条 1×1+3×3 路径），部署阶段可以比 v8 快 20-40%。

**结论**：想训练快 → v8s；想推理快 → v11s/n。

### Q3 · 为什么 v10 的精度不如 v8？

看 v10 官方数字（s 档 COCO）：v8s 50.2 AP，v10s 48.3 AP。**降了约 2 个 AP**。

原因是 v10 为了 **NMS-free** 端到端推理，改掉了 DFL（分布焦点损失），也简化了双头分配器。作者论文里明确说"以精度换推理速度"。

**取舍**：
- 想要**最高精度**：v8s / v11s
- 想要**NMS-free 极简推理链**：v10
- 想要**工程化 NMS-free**：v26（用 `reg_max=1` 兼容既有生态）

**参考**：[对比矩阵·损失函数演进](/compare-matrix#损失函数演进)

### Q4 · 为什么 v26 说自己是"最终形态"？

v26 是**首个 8 任务统一 backbone**（Detect / Segment / Pose / OBB / Classify / Depth / Semantic / YOLOE），也首个**内嵌 YOLOE** 的官方线。

"最终形态"不是精度最高（v11x 精度更高），而是**任务覆盖最广**——一个模型能跑所有主流检测任务。

但**部署谨慎**：v26 的 End2End 头量化后 topk 需要重调（见 [故障排查 · 量化](/troubleshooting#b-量化--精度)），且官方文档尚在完善中。

**参考**：[v26 全景](/versions/v26/index)

## 推理 & 部署

### Q5 · 为什么 v8 在 INT8 下精度掉得比 v11 多？

**v8s INT8 掉 0.5-1.0 AP**，v11s INT8 掉 0.5-1.2 AP——v11 甚至更差一点。

真正的问题不是版本，是 **DFL 层**：DFL 用 64 维分布预测框边长，INT8 量化后分布尾部被截断，长尾框（细长、扁平）抖动严重。**必须让 DFL 层保持 FP32**。

v8s 和 v11s 都有 DFL，所以问题一样；只是 v8 的 DFL 层数少，抖动幅度看起来稍小。

**参考**：[故障排查 · DFL 量化抖动](/troubleshooting#b-量化--精度)

### Q6 · 为什么 TensorRT 导出的模型比 PyTorch 慢？

99% 是这三个坑：

1. **`half=True` 没开**：TensorRT 默认 FP32，必须显式 `yolo.export(half=True)` 才走 FP16，速度能翻倍。
2. **`dynamic=True` 没设**：动态形状让 TensorRT 每次都重编译。固定输入尺寸 `dynamic=False` 反而更快。
3. **`device` 用错**：`device=0` 是 GPU 0，但如果你有多卡要用 `device=0,1` 或指定具体的 `cuda:X`。

**最快导出命令**：
```bash
yolo export model=yolov8s.pt format=engine half=True dynamic=False device=0
```

**参考**：[ONNX / TensorRT 部署](/recipes/export-onnx)

### Q7 · 为什么 Jetson 上比桌面 GPU 慢 10 倍以上？

**Jetson Orin Nano 8GB** 推理 v8s@640 约 25ms，桌面 RTX 4090 约 3ms。**差距 8 倍**，正常。

原因：
1. **算力差距**：Orin Nano 1024 CUDA cores，4090 是 16384，差 16 倍。
2. **带宽差距**：Orin 102GB/s LPDDR5，4090 1008GB/s HBM2e，差 10 倍。
3. **显存压力**：Orin Nano 8GB 是全系统共享的（CPU + GPU + Display），实际可用约 4GB。

**边缘部署的正确姿势**：
- **不要**直接用 v8m/l/x 的 FP32 权重
- **要**先 QAT 量化到 INT8（精度损失 0.5-1 AP 但推理速度 2-3 倍）
- **要**导出 TensorRT engine，不是 ONNX

**参考**：[边缘部署案例](/cases/edge-deployment) · [部署指南](/recipes/export-onnx)

### Q8 · 为什么我在树莓派 / RK3588 上跑不动？

**树莓派 4B** 最高跑 v8n@320 INT8，约 5 FPS。**RK3588** 最高跑 v8s@640 INT8，约 25 FPS。**这些平台跑 v8s@640 FP32 是不现实的**。

**边缘硬件选型速查**：

| 硬件 | 最低可用模型 | 推荐输入 | 目标 FPS |
| --- | --- | --- | --- |
| 树莓派 4B | v8n INT8 | 320 | 5-8 |
| RK3588 | v8s INT8 | 640 | 25-30 |
| Jetson Orin Nano | v8s INT8 | 640 | 30-40 |
| Jetson Orin AGX 64GB | v8m INT8 | 640-1280 | 40-60 |
| RTX 4090 | v8x FP16 | 640-1920 | 100+ |

**参考**：[硬件选型表](/cases/edge-deployment#硬件选型)

## 版本选择

### Q9 · 我只想做一个 COCO 检测，用哪个版本？

**用 v8s**。理由：
- Ultralytics 官方主力，生态最完善
- PyTorch / ONNX / TensorRT / OpenVINO 全支持
- 社区教程最多，遇到问题搜得到
- 45.3 AP（官方 s 档）够用 99% 场景

**别选**：
- **v10**：NMS-free 是它唯一卖点，但精度低 2 AP
- **v14**：多相机学术线，工业部署坑多
- **v26**：功能最全但部署文档不完善，2026 版太新

**参考**：[选型决策树](/choose-a-model)

### Q10 · 我要做开放词表检测，用哪个？

**用 YOLO-World v2**（不是 v26 内嵌的 YOLOE）。理由：

- YOLO-World v2-X COCO zero-shot 47.1 AP，比 YOLOE 高 3-5 AP
- 部署走通（worldv2 支持 ONNX/TensorRT，worldv1 不支持）
- Ultralytics 8.1.39+ 有完整训练管线

**YOLOE**（v26 内嵌）适合：
- 已经用 v26 的项目，不想再引一个新模型
- 对精度要求不高、追求极简部署

**参考**：[YOLO-World 完整文档](/derivatives/yoloworld) · [YOLOE 完整文档](/derivatives/yoloe)

### Q11 · v26 值得现在上生产吗？

**看你的场景**：

- **多任务需求明确**（既要做检测又要做分割和 OBB）→ 值得试，一个模型搞定
- **只是普通检测** → 不建议，用 v8s / v11s 更稳
- **要 INT8 部署** → 谨慎，End2End 头量化后 topk 需重调

**决策规则**：如果任务单一且精度优先，v8s / v11s；如果任务多样且想省工程量，v26。

## 数据 & 增强

### Q12 · 我的数据集只有 500 张，怎么训？

**三条路**：

1. **少样本微调**：用 COCO 预训练权重，`epochs=100+`、`lr0=0.0005`、`batch=16`
2. **数据增强开满**：`mosaic=1.0, mixup=0.3, copy_paste=0.5, hsv_h=0.1` 等，让 500 张变"几千张"
3. **合成数据**：用 Roboflow / CVAT 的自动标注 + SAM 分割生成伪标签

**红线**：**不要用 mixup/copy_paste 训医疗或 PCB 场景**（会合成出解剖上不可能存在的怪对象）。

**参考**：[训练调优指南 · 少样本](/recipes/train#少样本微调)

### Q13 · 为什么我加了 Mosaic 增强反而精度更低？

**Mosaic 只在特定场景有效**：

- **有效**：自然场景、多尺度目标（COCO 就是主打场景）
- **无效/有害**：
  - **俯拍工业图**（PCB 拼 4 张会破坏元件语义）→ `mosaic=0`
  - **车道分割**（道路拼接后语义混乱）→ `mosaic=0.2`
  - **医疗影像**（器官位置固定，拼 4 张没意义）→ `mosaic=0`

**规则**：如果你的场景**空间关系重要**（相对位置、朝向、拓扑），Mosaic 大概率无效。

**参考**：[故障排查 · Mosaic 有害场景](/troubleshooting#a-训练--增强)

### Q14 · 我应该用什么样的输入尺寸？

**默认 640**，除非：

- **小目标密集**（<50px）→ 1280 或 1536，但推理成本 +3-4 倍
- **边缘设备**（Orin Nano 以下）→ 320 或 416
- **远距离检测**（无人机、监控）→ 1280 + `imgsz` 动态切换
- **PCB 精细缺陷**（<5px）→ 1536 起步，但显存要 32GB+

**代价表**：

| imgsz | FLOPs 倍数 | 推理耗时倍数 | 小目标 mAP 提升 |
| --- | --- | --- | --- |
| 320 | 0.25× | 0.3× | -5~10 AP |
| 640 | 1.0× | 1.0× | 基准 |
| 960 | 2.0× | 1.5× | +1~2 AP |
| 1280 | 4.0× | 2.5× | +2~4 AP |
| 1536 | 5.7× | 3.2× | +1~2 AP（边际下降） |

## 概念澄清

### Q15 · TAL 到底是什么？（v6 引入的"任务对齐"）

**一句话**：TAL（Task Alignment Learning）用一个"分类难度 × 回归难度"的复合分数来决定谁是正样本，比传统的固定 IoU 阈值更合理。

**传统做法**（v1-v5）：预测框和 GT 框 IoU > 0.5 就算正样本。
**TAL 做法**（v6+）：
```
attn_score = sigmoid(cls_score)^(0.5) × sigmoid(box_score)^(0.5)
topk=10 里 attn_score 最高的算正样本
```

**为什么更好**：v5 用 IoU 硬阈值时，一个"分类分 0.95、IoU 0.45"的框会被丢弃；TAL 会给这个框 0.5 左右的注意力分，让它进入 topk。**分类和回归被"共同考虑"**，训练更稳定。

**参考**：[v6 论文·TAL 详解](/versions/v6/index) · [术语表](/glossary#tal-任务对齐学习)

### Q16 · DFL 是什么？为什么它对量化这么敏感？

**DFL（Distribution Focal Loss）**：把框边长预测当成一个概率分布来学，而不是直接回归一个数。

**直观理解**：
- **传统**：预测 `x = 100.3`（一个数）
- **DFL**：预测 `[0.01, 0.02, 0.03, 0.10, 0.40, 0.20, 0.10, 0.04, 0.05, 0.05]`（10 个位置的分布），最后期望值 `E[x] = sum(i * p[i])`

**为什么量化敏感**：分布尾部（`p=0.01, 0.02` 这种小概率）在 INT8 量化下容易被截断到 0，导致期望值计算错误。对**细长框**（车道线、栏杆）影响最大，量化后抖动明显。

**解决方案**：DFL 层保持 FP32，其它层量化 INT8。

**参考**：[术语表](/glossary#dfl-分布焦点损失) · [故障排查·DFL 抖动](/troubleshooting#b-量化--精度)

### Q17 · Anchor-based 和 Anchor-free 到底选哪个？

**Anchor-free**（v6/v8/v11/v12/v13/v26）已成主流，**除非**：

- 你**必须复现 v5 论文**（老项目迁移）
- 你的目标**极小**（<20px）且数据量大——anchor-based 在极小目标上略强

**为什么 anchor-free 更好**：
1. **少一步 NMS 前的 anchor 生成**（推理快）
2. **不用预训练 K-means 找 anchor**（工程简洁）
3. **和 DFL 天然配合**（分布预测不需要 anchor 中心）

**参考**：[对比矩阵·检测头演进](/compare-matrix#检测头演进)

### Q18 · YOLOv8 和 YOLOv11 我该学哪个？

**学 v8**。理由：

- v8 是"工业界默认答案"，80% 生产项目用的都是 v8
- v8 的 C2f / DFL / TAL 是理解后续所有版本的基础
- v11 相对 v8 的改动（C3k2、SPyNet）更多是**工程优化**，核心思想一致

**学习路径**：先 v8 打透 → 再看 v11（了解骨干演进）→ 再看 v26（了解多任务统一）

**不要**：一上来就读 v26 的 8 个任务，会迷失。

**参考**：[小白入门](/for-beginners) · [v8 完整文档](/versions/v8)

### Q19 · 什么是 NMS-free？为什么这么重要？

**NMS（非极大值抑制）**是检测的后处理步骤：多个框选一个。NMS 的问题：
- **需要阈值**（IoU 阈值通常 0.5，很难选）
- **CPU 实现**，GPU 加速差
- **并行困难**（依赖前一步的框数量）
- **量化后阈值要重调**（分数分布变了）

**NMS-free** = 训练时就让模型学会"每个框独立打分、不重叠"，推理时不需要 NMS 后处理。

**版本对比**：
- **v10**：首次 NMS-free，用一致性双分配器
- **v11**：退回 NMS（工程权衡）
- **v26**：End2End 头，官方线 NMS-free

**代价**：NMS-free 精度略低（v10 s 档比 v8s 低 2 AP），但推理链极简。

**参考**：[对比矩阵·检测头](/compare-matrix#检测头演进)

## 常见误区

### ❌ "YOLOv8 是最好的"

**不对**。v8 是"最成熟 + 生态最好"，不是精度最高。v11x 精度比 v8x 高 1-2 AP，v13s 是学术线最新，v26 是唯一的多任务统一。

### ❌ "参数越多精度越高"

**不对**。v8s（11.2M）和 v8m（25.9M）在 COCO 上差 3 AP，但 v8x（88.5M）比 v8l（55.2M）只高 1 AP。**边际收益快速下降**。

### ❌ "训练精度越高部署后也越高"

**不对**。INT8 量化后 v8s 掉 0.5-1 AP，v13s 掉 1-2 AP（HyperACE 超图不友好）。**训练精度高的版本，部署后未必领先**。

### ❌ "YOLO 都能做目标检测"

**不完全对**。YOLO 家族从 v1 到 v26 是**演进关系**，每个版本支持的任务集不同：
- v1-v4：只支持 Detect
- v5-v13：Detect / Segment / Pose / OBB / Classify
- v26：以上全部 + Depth / Semantic / YOLOE

**参考**：[任务全景对比](/compare-matrix#任务广度对比)

### ❌ "训练越久精度越高"

**不对**。YOLO 训练有明确收敛点（通常 100-300 epoch），超过后开始过拟合。**看 val mAP 曲线，连续 50 epoch 不再提升就该停**。
