# 基准数据对照 · 数字驱动选型

从 COCO AP、参数量、端到端延迟到部署成本，把 [compare-matrix](/compare-matrix) 的定性推荐升级为**可量化的数据锚**。

> **这一页存在的意义**：[choose-a-model](/choose-a-model) 给的是"经验推荐"，[compare-matrix](/compare-matrix) 给的是"结构差异"，但**读者真正需要的是数字**：在目标硬件上跑同一档输入，谁更快、准多少、贵多少。这里把本站点已知的**可验证数字**汇总成可查表，并标注每条数据的来源与采集状态。

---

## 一句话总纲

**基准数据的四层递进：COCO AP（能不能用）→ 硬件延迟（能不能实时）→ 量化精度保持（能不能上线）→ 部署 TCO（值不值得做）**。任一层的数字缺失，选型都要打折。

**本页最重要的原则**：**宁缺毋滥**。凡是没有可验证来源的数字，本页**明确标"待实测"或"占位"**，不给读者伪造的锚点。

## 数据来源与可信度

| 来源标记 | 可信度 | 说明 |
|---------|-------|-----|
| 🟢 **官方** | 高 | Ultralytics 官方 docs / 论文作者的 COCO 报告 |
| 🟡 **案例实测** | 中高 | 本站 [cases/compare](/cases/compare) 9 案例的真实项目数据 |

**读表提示**：
- 官方 AP 数字来自各版本论文或 Ultralytics docs 的 COCO 验证结果
- 延迟数字依赖 **输入分辨率 + 硬件 + 精度（FP32/FP16/INT8）+ 推理框架 + batch size**——任一变量不同，数字会差 2-5 倍
- 所有延迟默认指 **单张 640 输入、batch=1、warm-up 后** 的稳态平均

## 第二层：硬件延迟矩阵

**核心原则**：**跨硬件的延迟数字，必须指定 6 个变量才能复用**：

1. 输入分辨率（640 / 1280 / 1920）
2. 精度（FP32 / FP16 / INT8 PTQ / INT8 QAT）
3. 推理框架（TensorRT / ONNX Runtime / TFLite / RKNN）
4. 框架版本（TensorRT 8.x / 9.x / 10.x 差 15-30%）
5. Batch size（batch=1 和 batch=32 性能差异巨大）
6. Warm-up 后稳态（首次调用会慢 3-10 倍）

## 第三层：算力档位 → 模型档位映射

**把 TOPS 换算成"能跑什么"**——这是经验范围，不是精确数字：

| 算力（TOPS） | 典型硬件 | n 档 FPS | s 档 FPS | m 档 FPS | l/x 档 |
|-------------|---------|---------|---------|---------|-------|
| < 1 | 树莓派、手机 | 20-30 | ❌ | ❌ | ❌ |
| 1-3 | Jetson Nano、Xavier NX | 60+ | 20-40 | 5-15 | ❌ |
| 3-10 | Jetson Orin Nano | 100+ | 45-60 | 15-30 | ❌ |
| 10-50 | Orin 64GB、RTX 3060 | — | 60+ | 30-60 | 15-30 |
| 50+ | A100、H100 | — | — | 60+ | 30+ |

**决策**：
- **< 1 TOPS** → 只能选 n 档 + INT8 + 640 输入
- **1-3 TOPS** → n 档 FP16 或 s 档 INT8
- **3-10 TOPS** → s 档 FP16（生产甜点）
- **10-50 TOPS** → m 档 FP16 或 l/x 档 INT8
- **50+ TOPS** → l/x 档 FP16

**注意**：上表是**同精度下**的估算范围。切换精度（FP32 → FP16 → INT8）通常有 2-4x 提升。

## 第四层：量化精度保持

### 关键层保护清单（🟡 来自 9 案例反哺）

| 层类型 | 保护精度 | 不保护后果 | 涉及版本 | 反哺案例 |
|--------|---------|-----------|---------|---------|
| **DFL** | FP32 | 车道线抖动 2cm→6cm | v8/v9/v11/v12/v13/v14 | [autonomous-lane](/cases/autonomous-lane) |
| **AAttn** | FP16 | 分数曲线整体右移 | v12 | [medical-lesion](/cases/medical-lesion) |
| **HyperACE** | FP16 | 掉点 1-2%，QAT 补不回 | v13 | [industrial-defect](/cases/industrial-defect) |
| **NMS IoU 阈值** | 需重校准 | 0.5 阈值变严、召回下降 | 全部 NMS-based | [edge-deployment](/cases/edge-deployment) |
| **End2End topk** | FP16 | 端到端分配失败 | v26 | ⚪ 待反哺 |
| **CircularConv** | FP16 | 多视角对齐错位 | v14 | ⚪ 待反哺 |

### PTQ vs QAT 的经验法则

**这里给的是"经验区间"，不是具体数字——具体掉点因数据分布而异**：

| 版本 | PTQ 掉点经验区间 | QAT 可行性 | 说明 |
|------|---------------|----------|-----|
| v8 | 0.5-1.5% | ✅ 稳定 | 量化友好度标杆 |
| v11 | 0.5-1.5% | ✅ 稳定 | C3k2 stride 变化需校准 |
| v13 | 1.0-3.0% | ✅ 但需调 | HyperACE 需保留 FP16 |
| v26 | 0.5-2.0% | ✅ 但需调 | End2End topk 需重调 |
| v14 | ⚪ 未大规模实测 | ⚠️ 谨慎 | CircularConv 需自定义 kernel |

**规则**：
- **PTQ 是"试试看"**——用 500-1000 张代表数据校准，5 分钟出结果
- **QAT 是"正式上线"**——训练时插入伪量化节点，慢 3-5 倍但保精度
- **不要在生产环境用 PTQ 做基线**——生产环境的 INT8 数字必须以 QAT 为准

## 七种"看似合理"的选型错误

用本站已验证的数字戳穿常见误区：

### 1. "我要最高精度，选 v13x"
- **数据**：v13x 的 COCO mAP 57.0 vs v8x 的 57.9——**v8x 反而更高**
- **原因**：v13 是"注意力 + 深度可分离"路线，v8 是"梯度富集 C2f"路线，两者在 mAP 上互有胜负，v8x 依然是精度天花板
- **教训**：**"新版本"不等于"高精度"**

### 2. "v11 比 v8 更新，一定更好"
- **数据**：v11s mAP 49.7 < v8s mAP 50.2，v11x mAP 57.3 < v8x mAP 57.9
- **原因**：v11 的进步在**推理速度和参数量**，不在 mAP
- **教训**：**v11 适合速度敏感场景，v8 适合精度敏感场景**

### 3. "640 是默认，就用 640"
- **数据**：[industrial-defect](/cases/industrial-defect) 案例里 640 输入召回 PCB 小缺陷 <60%，1280 输入能到 90%+
- **原因**：小目标 < 32×32 像素在 640 输入下几乎无法被 P3/P4/P5 head 检测到
- **教训**：**先算数据集的小目标占比**，>30% 就必须上 960 以上

### 4. "INT8 掉点 <1% 就能上"
- **数据**：[industrial-defect](/cases/industrial-defect) 反哺里 v13s INT8 掉点 >1.5%（PTQ）
- **原因**：HyperACE 超图层的量化损失不是 PTQ 能解决的
- **教训**：**INT8 掉点必须 QAT 后重新测**，PTQ 只是初步筛选

### 5. "A100 比 Orin AGX 强很多"
- **数据**：[autonomous-lane](/cases/autonomous-lane) 案例里 Orin AGX 上 v11x 双头 78ms，已满足车端 30fps
- **教训**：**别为边际性能溢价**，Orin AGX 的车端性价比是 A100 的 5-10 倍

### 6. "训练 300 epoch 收敛最稳"
- **数据**：COCO 官方训练 100 epoch，>200 epoch 通常过拟合 3-5%
- **教训**：**100 epoch 是默认**，>200 epoch 需要早停

### 7. "选 v26 就省事了，多任务统一"
- **数据**：v26 数字待官方发布
- **教训**：**多任务场景选 v26**，单任务场景选 v8x / v13x / v11x

## 数据的局限与更新机制

**本页数据的已知局限**：

1. **数字会过时** —— Ultralytics 每 3-6 个月会更新模型权重，本页数字需要定期校准
2. **硬件差异大** —— 同一型号的 Jetson Orin 4GB / 8GB / 16GB / 32GB / 64GB 性能差 30-50%
3. **框架版本影响大** —— TensorRT 8.x / 9.x / 10.x 性能差 15-30%
4. **训练集偏差** —— 本页主要用 COCO，其他数据集（LVIS、OpenImages、行业数据集）数字会差 5-15%
5. **本页有 ⚪ 占位** —— 这些位置故意留空，等你或社区实测后回填，避免伪造数据

**首次采集日期**：2026-08

**更新机制**：
- 每季度 review 一次数字，标记已变化的条目
- 官方 benchmark 脚本 → [docs.ultralytics.com/benchmarks](https://docs.ultralytics.com/benchmarks)
- 欢迎通过 PR 回填 ⚪ 占位，标注：日期、硬件型号、TensorRT/框架版本、batch size、精度

**给读者的建议**：
- 本页数字用于**建立量级感**（v8s 在 Orin 上是 12ms 量级，不是 120ms 量级）
- **具体数字请用你自己的硬件和推理框架实测一次**再决策
- Ultralytics 提供官方 `yolo benchmark` 命令，见第 2 层"用户环境实测配方"
